# ADR-0001：技术选型与许可证

- **状态**：已接受
- **日期**：2026-10-07
- **决策者**：项目发起人

---

## 背景

需要一个跨 Windows / macOS / Linux 的本地照片资产管理工具，能力涵盖 RAW/HEIC 解码、缩略图缓存、人脸识别、AI 语义检索、时间线/地图/相似聚类、元数据编辑导出，并支持第三方插件扩展。定位为面向发布、开源、多人协作的产品。

## 决策

### 1. 外壳：Tauri v2

**选择**：Tauri v2（Rust 核心 + 系统 WebView）

**理由**：
- 安装包 ~15MB，常驻内存约为 Electron 的 1/5。照片工具要长时间常驻，这个差距是决定性的。
- 图像处理在 Rust 侧完成，跨平台复用一套代码，不需要为每平台维护一套原生插件。
- 共享 Rust 核心让"索引/流水线/插件运行时"这些真正难的部分只写一次。

**代价**：WebView 行为在三平台有细微差异；复杂交互调试不如 Electron 直接。

**备选**：Electron（生态最全但资源开销大）、本地 Web 服务（滚动性能与系统集成不足）。

### 2. 前端：React + TypeScript + Vite

**选择**：React 18 + TS + Vite，TanStack Query / Virtual 管状态与虚拟滚动

**理由**：插件作者的基数直接决定生态规模。React + TS 是这个领域唯一无需解释的选择。

### 3. 图像：libvips（经 rust-vips）

**选择**：libvips 作为统一解码与缩放管线，链接 libheif（HEIC/AVIF）、libraw（RAW）

**理由**：缩略图吞吐是用户体验的胜负手。libvips 的 `shrink-on-load`（JPEG DCT 直接降采样）在解码阶段就缩放，比"全解码再缩放"快一个数量级。纯 Rust 方案（如 `image` crate）在这一环目前没有等价物。

**代价**：
- 原生依赖构建是三平台发版的最大摩擦，缓释手段见下。
- libvips / libheif / libraw 均为 **LGPL-2.1+**，必须动态链接（见 §5）。

**备选**：纯 Rust（`rawler` + `image` + `zune-jpeg`）。许可更干净，但在 RAW 全量解码与智能降采样上要自己补，估算多 3–4 周且性能不可控。保留为"无原生依赖便携版"的降级路径。

### 4. 索引：SQLite + FTS5 + sqlite-vec

**选择**：单文件 SQLite，WAL 模式；文本检索用 FTS5，向量检索用 sqlite-vec（HNSW）

**理由**：零运维、单文件可直接备份、迁移即拷文件。sqlite-vec 是单个 C 文件的扩展，易于三平台打包，比引入 LanceDB 这类独立存储引擎简单得多。

**量化**：10 万张 CLIP 向量（int8 量化，512 维）约 50MB，完全可接受。

### 5. 许可证：AGPL-3.0-or-later

**选择**：宿主与 SDK 全部 AGPL-3.0-or-later。

**理由**：产品定位是"面向发布、开源、多人协作"。AGPL 保证任何网络服务形态的分叉也必须开放源码，防止出现"社区养生态、公司闭源收割"的结果。这是生态可持续的前提，不是对贡献者的敌意。

**衍生约束**：
- libvips / libheif / libraw（LGPL-2.1+）**必须动态链接**，不得静态内联进主二进制。
- 发行包内必须包含第三方组件声明与对应源码获取入口。
- CI 增加一项检查：确认主二进制未静态链接上述库。

**已否决**：MIT / Apache-2.0（无法约束闭源分叉）。若未来引入官方闭源增值服务，仍保持 AGPL 主体 + 独立仓库承载闭源部分。

### 6. 推理：ONNX Runtime（Rust `ort`）

**选择**：ONNX Runtime 绑定，本地 CPU 推理，模型按需下载

**理由**：`ort` 是 Rust 侧最成熟的推理绑定；ONNX 生态的模型可直接复用，换模型不必重写推理代码。

**约束**：模型权重**不进安装包也不进仓库**（体积 + 许可），改为后台可续传下载 + 本地模型注册表。用户显式下载即视为接受该模型许可。

### 7. 插件：QuickJS 沙箱

**选择**：QuickJS（`rquickjs`）进程内执行，独立线程池 + 三重资源限额 + 能力网关

**理由**：内存安全、无宿主内存可达性、可设内存/栈/指令上限、运行时仅 ~2MB。第三方插件跑在宿主进程内是生态效率的必要代价，用隔离和限额来兜住风险，而不是靠信任。

**关键约束**：能力在网关层强制，不在插件层自觉。文件系统走虚拟路径 + 授权子树；数据库走只读 SQL AST 白名单；网络默认关闭，按 manifest 声明的域名放行。

**同进程 vs 子进程**：协议定义一次。默认 QuickJS 进程内；同时预留"严格模式"——同一份插件产物跑在 Deno 子进程中，用于不信任的插件。协议不变，生态不被实现细节绑架。

### 8. 原生依赖分发

**选择**：`native-deps/` 存放三平台 × 双架构的预编译二进制，CI 校验 SHA-256

**理由**：三平台源码构建 libvips 是发版阻塞点。预编译 + 校验和把构建时间从小时级降到秒级，且可复现。

**风险**：预编译二进制是供应链攻击面。缓解：校验和强制校验、来源为项目自有私有仓库、二进制更新走独立 PR 评审。

## 影响

**正面**
- 一套 Rust 核心覆盖三平台，图像与索引逻辑零重复。
- 性能预算（见 ROADMAP §3）在当前选型下可达标。
- AGPL + 生态友好的插件 API，利于长期吸引贡献者。

**负面**
- 原生依赖分发需要持续的维护投入。
- LGPL 动态链接对打包与发布流程有硬性要求，不可绕过。
- QuickJS 同进程执行意味着插件 bug 可能波及宿主，看门狗与限额是必需品而非可选项。
